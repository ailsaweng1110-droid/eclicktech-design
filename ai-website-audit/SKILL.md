# 官网 AI 友好度诊断专家

## 目标

诊断目标官网在 AI 大模型视角下的可读性、可理解性与可引用性，从**设计侧、内容侧、技术侧**三个维度给出结构化评估报告，最终目的是让官网能够被 AI 大模型**主动推荐、有效抓取、准确引用**。

> **⏱ 运行说明**：全站诊断预计 **30～60 秒**（6 次网络请求）。已针对速度深度优化：robots.txt/sitemap 不主动抓取；报告/博客页按需才抓；Step 4+5 合并为 2 次搜索。

本 Skill 需要两个网络能力 + 报告展示能力。**根据你所在的平台按下表选择调用方式：**

### 网络能力（必需）

| **读取网页**（`fetch_page`） | 使用内置 `web_fetch` 工具 | `GET https://r.jina.ai/{完整URL}` |

### 跨平台质量保障原则

**无论哪个平台，最终必须保证：**
1. 诊断流程完全一致（Step 0～9）
2. 评分体系完全一致（设计20% + 内容40% + 技术40%，各项满分10分）
3. 报告内容结构完全一致（核心结论 → 评分明细 → 优化建议 → 文件草稿）
4. 可交付的 llms.txt 和 ai-page.md 文本内容完全一致

**唯一差异**：呈现方式——Claude.ai 有富交互组件，其他平台用 Markdown 表格/列表/代码块呈现同样信息，不影响诊断质量。

## 诊断流程总览

```
Step 0  行业识别     → 查内联权重表，0 次网络请求
Step 1  llms.txt     → 1 次 fetch_page（robots.txt/sitemap 改为手动核实项，不占用请求）
Step 2  页面抓取     → 3 次 fetch_page：首页 + 关于页 + 案例页
                       （报告/博客页按需补抓；首页新闻区已覆盖时效性评估）
Step 3  内容还原     → 0 次网络（基于 Step 2 已有数据）
Step 4+5 认知+跨平台 → 2 次 search_web：①公司名+业务，②行业推荐测试
Step 6  三维度评估     → 0 次网络
Step 7  综合评分     → 0 次网络
Step 8  优化建议     → 0 次网络
Step 9  文件+报告     → 读取 report-template.md，生成报告

总网络请求：6 次（上次优化后 9 次 → 现在 6 次），预计耗时 30‑60 秒
```

## Step 0：行业识别

读取 `references/industry-weights.md`，根据官网 URL 和已知信息（或用户描述）初步判断行业类型。若仅凭 URL 无法判断，记录"待确认"，在 Step 2 抓取首页后根据首页内容完成最终判断，然后继续 Step 2 的其余页面抓取，不需要回头重新执行 Step 0。

**常见行业权重速查（无需读取参考文件）：**

| 行业 | 设计 | 内容 | 技术 |
|------|------|------|------|
| 出海营销 / 广告服务 | 20% | 45% | 35% |
| SaaS / 软件产品 | 20% | 35% | 45% |
| 跨境电商平台 | 25% | 40% | 35% |
| 企业服务 / 咨询 | 20% | 50% | 30% |
| 品牌 / 消费品电商 | 30% | 40% | 30% |
| 通用默认 | 25% | 40% | 35% |

混合型（命中2个行业）：取两行业权重平均值。命中3个及以上：用通用默认权重。

**混合型公司处理规则**：若同时命中两个行业特征，将两个行业的权重分别取平均值作为最终权重。例如，同时命中"出海营销"（设计20% / 内容45% / 技术35%）和"SaaS产品"（设计20% / 内容35% / 技术45%），最终权重为设计20% / 内容40% / 技术40%。若命中三个及以上，使用通用默认权重（设计25% / 内容40% / 技术35%）并在报告中注明。

## Step 1：llms.txt 检查（首个网络请求）

> 💬 播报：「正在检查 llms.txt…」

调用 **fetch_page(`域名/llms.txt`)**：
- **404** = 确认未部署，技术侧 llms.txt 项得 1 分
- **200** = 已部署，读取内容评分
- **403 / 其他** = 无法验证，标注"工具权限限制"，不扣分

**robots.txt 和 sitemap.xml 不在此处抓取**——工具对这两个路径的 403 率极高，会白白消耗 2-10 秒。改为在报告"如何自行核实"中提示用户手动访问，评分时标注"无法验证"。

> **P0 警告例外**：若用户明确反馈 robots.txt 存在 AI 爬虫封锁问题，可补充抓取并在报告顶部标注 P0 警告。

---

## Step 2：全站核心页面抓取

> 💬 播报：「正在抓取核心页面（首页+关于+案例+报告，共 4 页）…」

调用 **fetch_page(URL)** 读取页面，获取 Markdown 格式内容。

**本诊断默认对整个站点评估**，内容侧评分基于全部已抓取页面的综合信息，而非单一页面。抓取遵循以下三层策略：

### 技术文件（已在 Step 1 完成 llms.txt）

sitemap.xml 不主动抓取，在报告核实框中提示用户手动访问 `/sitemap.xml` 确认。

### 第二层：核心导航页面（从首页导航自动识别路径，存在则抓取）

**首先抓取首页**，抓完后立即执行多语言判断，再继续抓取其余页面。

#### 多语言判断（首页抓取完成后立即执行，不等其余页面）

检查首页导航中是否存在语言切换入口（如"EN"、"中文"、语言图标等），按以下规则确定本次诊断语言：

- **有中文版本**：默认诊断中文版本，继续抓取其余页面。
- **无中文、有英文版本**：默认诊断英文版本，继续抓取其余页面。
- **发现其他语言版本**：完成当前版本的完整诊断后，在报告**末尾**统一询问用户：「检测到该官网还有 [语言列表] 版本，是否需要继续诊断？」
- **用户主动要求诊断多个版本**：按顺序逐个完整执行 Step 1～Step 8，每个版本出具独立报告；若完成后用户希望看到版本对比，在所有报告之后追加"多版本对比"模块；若多个版本共用同一主域名，robots.txt 和 llms.txt 可复用同一抓取结果，无需重复抓取。

#### 核心导航页面

**必抓（3页，覆盖85%评分所需信息）：**

| 页面 | 路径示例 | 主要贡献 |
|------|---------|---------|
| 首页 | `/` | 设计结构、核心数字、品牌呈现、近期新闻（含时效性评估） |
| 关于页 | `/about`、`/html/aboutus` | 公司事实密度、创始团队、E-E-A-T 信任信号 |
| 案例页 | `/case`、`/html/case` | 可引用性、量化数据 |

**按需补抓（以下情况才追加）：**

| 页面 | 补抓条件 |
|------|---------|
| 博客/报告页 | 首页无近期新闻/报告，无法评估时效性时 |
| 产品/服务页 | 首页未见具体服务描述时 |
| 解决方案页 | 评估垂直行业内容有疑问时 |

> **顺便检查重复 title/meta**：在抓取多个页面时，如果注意到不同页面的 title 或 meta description 完全相同，应在 Step 6 中标注"重复 title/description 问题"，这是 CMS 系统的常见失误。

> **注意**：上述页面类型并非每个网站都具备，根据首页导航实际存在的页面抓取，不强行寻找。抓取案例页和博客时，只抓索引页，不逐篇抓取单篇文章。若索引页无内容摘要，可抓取 1～2 篇最新文章作为代表样本。

### 第三层：补充页面（按需抓取）
若第二层抓取后仍有以下评估项无法判断，则补充抓取对应页面：
- 联系页（用于获取邮箱、地址等事实信息）
- 产品技术页（用于判断技术能力描述的准确性）

### 竞品对比（可选）
若用户提供了竞品 URL，提供两种模式，未说明时默认快速对比：
- **快速对比（默认）**：仅抓取竞品首页，执行 Step 3 + Step 6，在本站报告中新增竞品对比列。额外耗时约 30～60 秒。
- **完整诊断（用户主动要求）**：对竞品同样执行全站核心页面抓取 + Step 1～8，出具独立竞品报告。额外耗时约 2～5 分钟。

若用户仅描述网站内容（无 URL），基于描述诊断，报告中标注"基于描述诊断，建议提供 URL 进行精准分析"。

## Step 3：Markdown 内容还原（AI 视角近似预览）

> 💬 播报：「正在还原 AI 视角内容预览，识别内容盲区…」

基于 Step 2 获取的全站页面内容，选取**首页**作为 AI 视角预览的展示对象（首页是 AI 爬虫最优先抓取的页面，最具代表性）；其余页面的内容用于 Step 6 评分，不在预览中逐一展示。

在预览统计区域注明：「当前预览为首页，评分基于全站已抓取的 N 个页面」。

> **准确性说明**：fetch_page 返回的 Markdown 是 AI 爬虫视角的**近似还原**，非精确等价于 HTML 源码——工具会过滤部分隐藏元素。本步骤帮助用户直观感知内容可读性。报告中需注明"以下为近似视图"。

### 保留与处理规则

- 导航菜单 → 替换为 `<!-- 导航菜单 -->`
- Footer → 替换为 `<!-- 页脚 -->`
- 表单字段 → 丢弃
- `display:none` 的文字 → 尽量保留（AI 读 HTML 源码，不执行 CSS）
- 有 alt 文字的图片 → `[图片：alt内容]`

### 盲区标注

- 视频 / Canvas / WebGL 无文字副本 → `[⚠️ 视频或动画，AI 不可读]`
- 图片无 alt → `[⚠️ 图片，无文字描述]`
- JS 动态注入区域 → `[⚠️ 此内容需操作后加载，AI 不可见]`

### 完整保留原则

**针对首页预览内容：不截断，不省略**。无论首页内容长短，都完整输出全部还原内容（其余已抓取页面不在预览中展示，其内容用于 Step 6 评分）。

**实现方式（按平台）**：
- **Claude.ai**：调用 `show_widget` 工具，以固定高度容器 + `overflow-y: auto` 展示滚动视图
- **其他平台**：将近似视图放在 Markdown 代码块中（```）输出给用户，保持等宽字体和缩进即可

不能只在对话正文中输出普通 Markdown 文本（对话正文无法清晰区分盲区和正常内容）。**按平台选择**：Claude.ai 用 show_widget 容器；其他平台用 ````text` 或 ````markdown` 代码块包裹呈现

报告组件实现要求：
- 预览容器高度固定为 320px，`overflow-y: auto`
- 容器使用等宽字体（`font-family: var(--font-mono)`）
- 背景使用次级背景色（`var(--color-background-secondary)`），视觉上明显区分为"原始内容"展示区
- 盲区标注（`[⚠️ ...]`）用amber色高亮显示，与正常内容形成对比

### 干货密度判断标准

- **高**：剥离后有大量事实性文字，AI 可独立理解公司全貌
- **中**：有基础信息但不完整，部分内容藏于盲区
- **低**：剥离后几乎只剩导航和数字，AI 无法形成有效认知

## Step 4+5：AI 认知测试 + 跨平台核查（合并执行，共 2 次搜索）

> 💬 播报：「正在测试 AI 认知与跨平台信息一致性…」

**⚡ 速度说明**：Step 4 和 Step 5 合并为 2 次搜索。第①次搜索结果同时用于两个 Step。

### 搜索①：公司认知 + 跨平台（1次搜索，两用）

调用 **search_web("[公司名] [核心业务关键词]")**（如"易点天下 出海营销"）

从同一组搜索结果中**同时提取**：
- **认知准确性**（Step 4a）：AI/媒体如何描述公司定位、成立时间、核心业务
- **跨平台口径**（Step 5）：百度百科摘要、天眼查摘要 通常直接出现在搜索结果里，直接提取，无需额外 fetch_page
- 若百度百科摘要信息不足，才单独 fetch_page 词条页（1次额外请求）

### 4a. 公司认知判断

从搜索①结果中判断：AI 当前描述是否准确？是否有核心业务遗漏或错误信息？

### 搜索②：行业推荐测试（Step 4b）

根据行业类型，搜索 **1～2 个**最有代表性的推荐类问题（无需穷举）。优先选覆盖面最广的问题，如“[行业] 服务商推荐 2026”。

**各行业推荐类搜索示例**

| 行业类型 | 搜索示例 |
|---------|---------|
| 出海营销 / 广告服务 | "出海营销服务商推荐"、"企业出海广告投放哪家好" |
| SaaS / 软件产品 | "[产品品类] 工具推荐"、"[功能关键词] 软件哪个好" |
| 跨境电商 | "跨境电商服务商推荐"、"亚马逊运营服务商" |
| 企业服务 / 咋询 | "[行业] 解决方案提供商"、"[服务类型] 咋询公司推荐" |
| 品牌 / 消费品 | "[品类] 品牌推荐"、"[使用场景] 产品哪个好" |
| 其他 | 根据官网核心业务自行拟定 1～2 个推荐类问题 |

**输出判断**：

| 搜索问题 | 目标公司是否出现 | 位置 | 同场出现的竞品 |
|---------|--------------|------|------------|
| [问题1] | ✅ 出现 / ⚠️ 未出现 | [第N条 / —] | [竞品A / 竞品B / —] |

- 目标公司出现 → ✅ GEO 曝光正常
- 目标公司未出现，但竞品出现 → ⚠️ GEO 差距明显，在优化建议中说明与哪些竞品存在差距
- 目标公司和竞品均未出现 → 该行业/场景整体 GEO 可见度低，属于行业普遍问题

> **说明**：以上搜索结果代表联网 AI（如 Perplexity、ChatGPT 联网模式）实时检索时的近似认知，非精确等价，但已是当前可操作的最有效验证手段。

## Step 5：跨平台一致性核查

> ✅ 已在 Step 4 搜索①中同步完成（百度百科/天眼查摘要已从搜索结果提取）。

**若 Step 4 搜索结果中信息不足，再补充：**
- 百度百科：单独 fetch_page 词条页 URL（重点查成立时间、定位描述）
- 英文站：搜索 Crunchbase / LinkedIn 摘要

核查重点：成立时间、公司定位、核心数字是否与官网一致；任何差异都是 AI 引用时的潜在错误来源。

如需完整平台清单，读取 `references/platform-checklist.md`。

## Step 6：三维度评估

> 💬 播报：「数据收集完毕，正在对设计侧 / 内容侧 / 技术侧逐项评分…」

**评分规则**：每项 0～10 分；各维度得分 = 该维度所有项目均分。
**权重**：读取 `references/industry-weights.md`，按行业类型使用对应权重；混合型按 Step 0 计算的平均权重。

> 📋 各评估项的详细分值锚点（什么是 9-10 分/什么是 3-4 分）见 `references/scoring-rubric.md`，每次打分前可按需查阅。

### 证据可信度规则（每个评分项都必须遵守）

报告的可信度来源于"证据可见、结论可验"。每个评分项的说明栏必须：

1. **引用具体证据**，而非泛泛描述。错误示例：「图片缺少 alt」。正确示例：「第二/三排合作伙伴 Logo 约24张（Snapchat/Pinterest/鲸鸿动能等）均无 alt；客户 Logo 轮播约36张无 alt」
2. **标注证据来源**，注明内容来自哪个页面（首页 / About 页 / 案例页等）
3. **区分证据可信度等级**，在说明中体现：
   - `✅ 直接验证`：通过 fetch_page 直接观察到的内容，用户可自行验证
   - `〜 推断`：基于可观察的间接信息推断，有一定不确定性
   - `⬜ 不适用`：该评估项对本站不适用（如单语言站的 hreflang 项），或工具权限限制无法验证；不计入评分分母，不扣分；报告中显示"不适用"并注明原因，取代原来的"N/A"缩写（用户不熟悉"N/A"含义）
4. **给出可验证操作**：对重要发现，提供用户自行核实的方法，如「在首页右键查看源代码，搜索 `alt=` 可确认覆盖情况」

### 全站评估原则

本诊断基于全站视角评分，不同类型的评估项有不同的取证范围：

| 评估项类型 | 取证范围 | 说明 |
|-----------|---------|------|
| **站点级技术项** | 根目录 / 全局 `<head>` | robots.txt、llms.txt、渲染方式、canonical、hreflang 属于全站配置，与具体页面无关 |
| **内容侧评估项** | 全部已抓取页面（取最佳证据）| 只要任一页面存在相关内容，即视为"网站具备"，评分时注明内容所在页面 |
| **设计侧·结构类** | 首页为主，其余页面参考 | 语义化结构、关键文字可爬取性、页面层级清晰度——首页承载最多流量，优先评估 |
| **设计侧·全站类** | 全部已抓取页面（统计整体情况）| 图片 alt 覆盖率、链接文字语义质量——任何页面的缺失都是问题，取全站综合表现 |
| **Meta 标签（含 OG）** | 首页 + 核心落地页 | 分别评估，综合取均分；若各页面质量差异大，在说明中注明 |

**内容侧"取最佳证据"的含义**：若"公司描述事实密度"这一项，首页缺少成立时间，但 About 页有，则视为"全站有该信息"，不给低分；评分说明里注明"成立时间见 About 页，建议同步至首页以提升 AI 首次抓取的完整性"。

| 页面加载与可达性 ⟨SEO⟩ | 核心页面快速可达；HTTPS 正常；无明显过重资源拖慢爬虫 |
| hreflang 标签 ⟨SEO⟩ | **仅当检测到多语言版本时评估**；已正确配置=9～10；缺失但路径清晰=5～6；完全缺失且有多语言=2～3；单语言站标"不适用" |

**SEO 增量项**（Claude 可有效检查的项目，纳入技术侧评分）

| 评估项 | 说明 |
|--------|------|
| title 字符长度 ⟨SEO⟩ | 首页及核心页面 title 是否在 50～60 字符以内（中文字符按 2 字符计算）；过长会被搜索引擎/AI 截断；过短传递信息不足 |
| meta description 质量 ⟨SEO⟩ | 是否存在且在 120～160 字符以内；内容是否事实性（非"欢迎来到XXX官网"）；缺失时搜索引擎/AI 自动摘取正文，效果不可控 |
| URL 结构可读性 ⟨SEO⟩ | URL 是否含语义化路径（如 `/about` 优于 `/html/aboutus?id=1`）；是否含不必要的动态参数；是否含中文字符（需转义，不利于引用） |
| sitemap.xml ⟨SEO⟩ | 是否存在且可访问；Step 2 第一层已尝试抓取；帮助爬虫发现全站页面；404=确认缺失 |
| 内链与锚文字 ⟨SEO⟩ | 核心页面之间是否有合理内链；锚文字是否有语义（与设计侧"链接文字语义质量"侧重点不同：此处关注页面互链结构，彼处关注 CTA 按钮文字） |
| viewport meta ⟨SEO⟩ | 是否有 `<meta name="viewport">` 移动端适配标签；缺失会导致移动端 Google 评分下降 |
| OG image ⟨SEO⟩ | 是否配置 `og:image`；影响内容在社交媒体和 AI 聊天中的展示效果；建议 1200×630px |
| 图片宽高声明 ⟨SEO⟩ | img 标签是否声明 width/height 属性；缺少宽高是 CLS（累积布局偏移）的主要来源，图片加载时会推挤周围内容；背景图（CSS background-image）不会被 Google 图片收录，重要产品图必须用 `<img>` |
| 内链 href 有效性 ⟨SEO⟩ | 内链是否使用标准 `<a href="...">` 而非 onclick/javascript:void(0)/javascript:; 等形式；Googlebot 无法抓取非标准链接，导致目标页面失去被发现的机会 |
| HTTP 状态码 / 软404 ⟨SEO⟩ | 核心页面是否返回 200；是否存在软404（页面内容显示"未找到"但状态码返回 200，严重浪费 Google 抓取预算）；删除的页面建议返回 410 而非 404 |
| URL 结尾斜杠一致性 ⟨SEO⟩ | 带斜杠（/about/）和不带斜杠（/about）被视为两个独立页面，必须通过服务器 301 重定向统一到一种格式；markdown 模式无法验证，需手动核查 Nginx/Apache 配置 |
| Nofollow 属性 ⟨SEO⟩ | 外链和 UGC 内容是否按需添加 rel="nofollow"；站内正常导航链接绝对不能加 nofollow，否则阻断内部权重传递；markdown 模式无法全面核查 |
| 分页处理配置 ⟨SEO⟩ | 是否提供静态可点击的分页 URL（如 /case?page=2）；纯 JS 无限滚动加载的内容爬虫无法看到后续页面；需配合 History API 或提供 `<a href>` 分页按钮 |
| Core Web Vitals（LCP/INP/CLS）⟨SEO⟩ | LCP<2.5s：首屏核心图用 preload，SSR 服务端直出；INP<200ms：拆分长任务，第三方脚本用 async/defer；CLS<0.1：图片/广告位预留宽高占位。**需 Google PageSpeed Insights 或 Lighthouse 检测，Claude 标注为"无法验证"** |
| 混合内容（HTTPS 页面内嵌 HTTP 资源）⟨SEO⟩ | HTTPS 站点中是否有 HTTP 协议的 JS/CSS/图片/字体/iframe；混合内容触发浏览器安全警告并被搜索引擎下调安全评级；**AI 爬虫也会因安全策略拒绝加载，影响 GEO 可见性**。Claude 无法直接检测资源加载协议，标注"无法验证"，建议用 Chrome DevTools→安全面板核查 |
| HTTP→HTTPS 全站重定向 ⟨SEO⟩ | 访问 http://domain.com 是否自动 301 跳转至 https://；HTTP/HTTPS 并存会分散页面权重。可尝试 fetch_page http:// 版本，观察是否重定向 |
| 外部链接有效性 ⟨SEO⟩ | 页面外链是否返回 200（非4xx/5xx）；失效外链降低内容可信度和权威性评级；AI 爬虫同样受失效链接影响。可在 fetch_page 返回内容中识别明显的 href 外链并标注，但批量验证需专业工具（Screaming Frog/Semrush）|
| 文本/HTML 比率 ⟨SEO⟩ | 页面有效文字内容占 HTML 总体积的比例；低于10%意味着几乎没有实质内容，搜索引擎无法判断页面价值。**与 AI 视角内容预览直接相关**：大量图片/视频无文字副本的页面，文本/HTML 比率必然极低。通过 fetch_page 返回内容密度可推断此项 |
| robots.txt 资源拦截风险 ⟨SEO⟩ | robots.txt 是否错误封锁 /static/、/css/、/js/、/images/ 等渲染必需资源目录；这是 CMS 默认配置的常见失误，导致爬虫无法渲染页面。Claude 在 Step 1 读取 robots.txt 时需专门检查 Disallow 规则是否包含资源目录 |
| 重复 title/meta description ⟨SEO⟩ | 多个页面是否共用相同的 title 或 meta description（模板化生成）；重复内容让搜索引擎无法区分页面主题，丧失长尾词覆盖机会。Claude 通过抓取多个核心页面对比 title/description 内容可检测 |
| 页面抓取深度 ⟨SEO⟩ | 核心业务页面从首页出发需要几次点击才能到达；超过3次点击爬虫和用户都难以触达，影响权重传递。Claude 通过分析导航结构和内链层级可推断 |
| meta refresh 元刷新重定向 ⟨SEO⟩ | 是否使用过时的 `<meta http-equiv="refresh">` 做页面跳转；此方式加载效率低且不符合搜索引擎规范，应替换为服务器端 301/302 重定向。在 fetch_page 返回内容中可检测 meta refresh 标记 |

## Step 7：综合评分

> 💬 播报：「正在计算综合评分…」

```
设计侧得分 = (语义化结构 + 关键文字可爬取性 + 页面层级 + 图片alt覆盖率 + 链接文字语义 + 排版可读性) / 6

内容侧得分 = (事实密度 + 可引用性 + 跨平台一致性 + AI友好摘要 + 时效性 + GEO首屏倒金字塔 + 语义实体覆盖 + 排版可读性 + 信任信号EEAT + 多语言内容一致性) / 10
            （多语言内容一致性为"不适用"时，分母为 9；各项"无法验证"同理剔除）

技术侧得分 = (robots.txt + llms.txt + Schema.org + Meta标签含OG + canonical + 渲染方式
             + 可达性 + hreflang + title字符长度 + meta_description质量
             + URL结构 + sitemap + 内链锚文字 + viewport + OG_image + 图片宽高声明 + 内链href有效性 + HTTP状态码软404 + URL结尾斜杠
             + Nofollow属性 + 分页处理 + Core_Web_Vitals) / 22
            （"不适用"项从分母剔除：hreflang 单语言站不适用；robots.txt/canonical/viewport 
             无法验证时不适用；以实际有效项数为分母）

综合评分 = 设计侧得分 × 设计权重 + 内容侧得分 × 内容权重 + 技术侧得分 × 技术权重
```

> **新增 SEO 增量项说明**：7 个 SEO 项纳入技术侧评分分母，客观上会使技术侧得分对缺失项更敏感。这是合理的——SEO 可见性与 GEO 可引用性底层基础设施高度重叠，缺失 SEO 基础配置同样损害 AI 抓取质量。

| 分段 | 等级 | 含义 |
|------|------|------|
| 85～100 | 优秀 | AI 可高效理解并主动引用 |
| 70～84 | 良好 | 有局部短板，修补后可达优秀 |
| 50～69 | 中等 | 存在明显缺失，需系统优化 |
| 50 以下 | 较差 | AI 理解受阻，建议重点改造 |

## Step 8：优化建议与优先级排序

> 💬 播报：「正在整理优化建议，按优先级排序…」

对所有评分低于 7 分的项目给出具体可落地的建议。每条必须包含以下五个要素：
- **所属维度**：`[设计侧]` / `[内容侧]` / `[技术侧]`
- **具体操作**：明确的行动步骤
- **背景**：1 句话说明为什么要做这件事，面向不熟悉 GEO 的用户
- **预估提升分值**：参考 `references/score-boost-reference.md` 的区间，结合当前得分给出估值
- **实施角色**：`[运营可操作]` / `[需前端介入]` / `[需后端介入]` / `[需全栈]`

**优先级标签**
- 🔴 P0 立即修复：阻塞 AI 抓取的根本性问题
- 🟠 P1 优先优化：显著影响 AI 理解质量
- 🟡 P2 计划推进：有助于提升引用率，可排期

## 注意事项

以下为容易遗忘或容易出错的关键提醒，完整规则见各 Step 详细说明：

- **robots.txt 必须先查**：Step 1 不可跳过；若 AI 爬虫被封锁，在报告顶部插入 P0 警告后继续诊断
- **无法验证 ≠ 未部署**：404 可给低分；403/超时/连接失败标"不适用"，不扣分，提示用户手动核查；**报告中统一显示"不适用"而非"N/A"缩写**，并附简短原因说明
- **证据必须具体**：每个评分项说明必须引用具体证据 + 标注 ✅/〜/⬜ 等级，不写泛泛描述
- **权重必须行业化**：综合评分必须使用 industry-weights.md 中的对应权重；混合型按平均权重计算
- **JS 渲染识别**：抓取到的内容极少但页面明显内容丰富时，判断为纯 CSR，渲染方式项给 3 分以下，列为 P0
- **跨平台核查不可跳过**：Step 5 必须实际执行，无法抓取的平台标注原因和建议操作
- **竞品诊断模式**：用户未说明时默认"快速对比"；用户主动要求时才执行"完整诊断"并告知额外耗时
- **抓取失败引导**：fetch_page 失败时必须告知原因和解决方法，说明该失败影响了哪些评估项
